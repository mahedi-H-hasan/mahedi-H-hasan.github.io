Publishing from a Branch Other Than Main

A working reference for editing this site on a topic branch, testing it locally, and — only when actually needed — manually deploying that branch to the live GitHub Pages URL instead of waiting for a merge to main.

Normal changes don't need any of this. Push to main and the Deploy to GitHub Pages workflow (.github/workflows/deploy-pages.yml) publishes automatically. The steps below are for the times you want to write and test on a separate branch first, or deploy a branch on demand without merging it.

1. Create and push a topic branch

  1. Branch from an up-to-date main

    Make sure your local main has the latest commits before branching, so the workflow file and site content you start from match production.

    git checkout main
git pull origin main
git checkout -b my-topic-branch

  2. Edit, commit, and push

    Work normally — edit the HTML/CSS/JS files, commit, and push the branch to GitHub.

    git add .
git commit -m "Describe the change"
git push -u origin my-topic-branch

2. Preview and test before deploying anything

This is a static site with no build step, so the most reliable way to review a branch is to serve it locally exactly as described in the project README: 

git checkout my-topic-branch
npx serve .
# or
python -m http.server 8000

Then open every page you touched (each is a standalone HTML file, e.g. http://localhost:8000/publications.html) and check the mobile nav toggle, current-page nav highlighting, and any content you changed.

Caveat

GitHub Pages itself has no separate "preview" environment or per-branch preview URLs for this repository — there is exactly one live Pages site, served from whatever was last deployed by the Actions workflow. A pull request opened for the branch does not get its own deployed URL. Local serving is the safe way to review a branch before anyone deploys it.

3. Manually deploy a chosen branch (when actually needed)

The Deploy to GitHub Pages workflow already listens for workflow_dispatch, GitHub's manual "Run workflow" trigger, alongside its normal push-to-main trigger. That lets you run it by hand against any branch that has the workflow file — without touching Pages settings.

  1. Make sure the branch has the workflow file

    workflow_dispatch only offers a branch in the "Use workflow from" list if that branch contains .github/workflows/deploy-pages.yml. Branching from an up-to-date main (step 1) already satisfies this, since the workflow file lives in this repo's history.

  2. Open Actions → Deploy to GitHub Pages

    In the GitHub repository, go to the Actions tab and select the Deploy to GitHub Pages workflow in the left sidebar.

  3. Run workflow → choose the branch

    Click Run workflow. In the dropdown, use Use workflow from to pick the branch you want to deploy (for example my-topic-branch), then type that exact branch name into the confirmation field the workflow asks for.

  4. Confirm and run

    Submit the run. The job checks that your typed confirmation matches the branch the run actually started from, then builds and deploys that branch's current files.

Important

This deploys straight to the same public production URL (mahedi-h-hasan.github.io) that everyone already sees — it is not a private preview. Whatever is in the chosen branch replaces the live site the moment the run finishes, and it can overwrite content that was previously deployed from main until someone deploys main again.

4. Restore production

If a manual deployment needs to be reverted, run the same workflow again — Actions → Deploy to GitHub Pages → Run workflow — but this time pick main in Use workflow from and type main in the confirmation field. That redeploys whatever is currently on main, putting the live site back to its normal, push-driven state.

No change to Settings → Pages is required for any of this — the source stays set to GitHub Actions throughout, and every push to main continues to deploy automatically exactly as before.
